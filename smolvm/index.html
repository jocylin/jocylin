01 · The Kernel Boundary

三次重写，每一次都因租户更不可信

每一代虚拟化的跃迁，都是把"共享什么"和"隔离什么"的边界重画一次。驱动力始终一样：新租户的可信度下降。裸机时代你信任全部代码；容器时代你信任自己写的代码；agent 时代，代码是 LLM 现写的，你一行没读过。

Docker 一位工程师在 2026 年 5 月写道："我在二十年里看着这个行业重建了三次信任模型。"共享 kernel 在容器时代没问题，因为威胁是你自己软件里的 bug，不是你刚请进门的租户带来的意外。他对结局的预判是：microVM 的争论会重走同一条弧线——争论大约一年，三年内成为常识。
内核边界三次上移：裸机 → 虚拟机 → 容器 → Sandbox
02 · The Isolation Frontier

性能的来源，永远是少做隔离工作

"做更轻的方案该砍哪层隔离"没有标准答案，只有一条连续光谱：每砍一层，换来更快的冷启动和更高的密度,但逃逸所需的漏洞类别也少一类。行业据此分裂成三种赌注,差异不在好坏,而在威胁模型与负载形态是否匹配。

产品介绍

  • 定位：Smolmachines 是面向 AI agent / 开发者工作负载的轻量级微型虚拟机基础设施，核心主张是“ship the machine, not just the code”：把软件、依赖和运行状态打包成一个可移植的 .smolmachine，在本地、云端或自部署环境中以硬件隔离方式运行。
  • 产品形态：开源核心是 smolvm CLI，支持在 macOS / Linux / Windows 上运行自定义 Linux 微型虚拟机；公开 README 显示其能力包括亚秒级冷启动、跨平台运行、弹性内存、单文件状态打包、OCI 镜像启动、SSH agent 转发、网络白名单和 GPU 试验支持。
  • 核心技术差异：BinBin 在通话中现场演示了约 0.2-0.23 秒启动 Linux VM，并强调其相对 Firecracker / Docker 的差异不是“又一个 sandbox API”，而是一个更底层的 VM primitive：本地可跑、可打包、可 fork，且资源按 workload 弹性增长/收缩。
  • 隔离价值：相对 Docker / container sandbox，Smolmachines 提供 VM/kernel 级隔离；创始人特别强调 agent 生成代码删除本机文件等场景下，最坏结果是删除 VM，而不是破坏 host machine。
  • 产品边界：创始人明确表示不适合 GPU 密集型、高精度低延迟金融负载或需要严格亚秒级数据库一致性的工作负载；更适合 agent、ephemeral workloads、安全隔离执行、off-the-cuff compute，以及需要本地/云端一致环境的开发者工作流。

GTM

  • 初始切入点：聚焦“agentic builders”，尤其是 YC 中做垂直 agent 的公司，例如 agents for analysts、real estate、enterprise workflows 等，这些团队需要隔离执行环境，但通常不想直接使用面向 infra engineer 的传统云产品。
  • 开发者优先 + 开源传播：smolvm 采用 Apache-2.0 开源，GitHub 截至 2026-07-02 有 4,115 stars / 188 forks；创始人计划继续开放 CLI 与 SDK，使 agent 可以直接通过命令行调用服务，降低网页控制台依赖。
  • 信任建设路径：创始人认为当前最大 gap 不是技术 demo，而是 production trust / battle readiness；短期目标是让更多真实 VM workload 跑在云上，累计到“百万级 VM load”来证明稳定性。
  • IOSG 关联机会：创始人在通话中主动提出希望 IOSG 及 portfolio 公司成为客户，因为大量 AI portfolio 都需要安全隔离基础设施；小额 check 对其价值在于建立合作激励和 portfolio adoption。

Traction

  • 开源热度：smol-machines/smolvm 于 2025-12 创建，2026-07-02 GitHub API 显示 4,115 stars、188 forks、52 open issues、910 commits，默认语言 Rust，最近 push 为 2026-07-02。
  • 商业化状态：创始人称已经商业化，按 usage 计费；客户今天正在每天启动“几千个 VM”，但未披露 ARR / MRR / 留存 / 付费客户数。
  • 客户样例：通话中提到 refresh.dev、Byteport 以及若干 YC agent 公司正在使用或接触中；这些名字来自自动转录，客户身份和付费状态仍需确认。
  • 产品性能证据：通话中现场 demo 启动约 0.2 秒；公开 README 声称 portable executable boots in <200ms，并在对比表中列出 smolvm boot time <200ms。
  • 融资 traction：创始人称已 raise $2.7M at $35M cap；Twenty opportunity 显示 IOSG 可参与额度为 $50k，round/opportunity amount 字段为 $50k。

商业模式

  • 计费逻辑：usage-based，按 active CPU、active memory、active disk 计费；创始人称如果用户租一台 1 CPU / 4GB VM 且 CPU 100% 使用，Smolmachines 会更贵，但如果 CPU active time 低于 20%-50%，会比传统租固定 VM 更便宜。
  • 成本优势来源：弹性 VM 与 fork 机制让资源消耗从 N x M 接近 M + X，即父 VM 只付一次基础 RAM / disk 成本，子 VM 主要付差量；这提升主机上的 workload packing density。
  • 价格相对位置：创始人表述为“更像 sandboxing companies，more expensive than Fargate, cheaper than EC2”；该表述需要用真实 pricing benchmark 复核。
  • 潜在扩展：短期是 agent sandbox / code execution，长期创始人希望成为更通用的 cloud primitive，替代部分 EC2 / Lambda / Docker deployment 场景。

竞对分析

Smolmachines 的 Edge 在于

  • 底层 primitive 差异：多数 agent sandbox 公司是在 Firecracker / gVisor / Docker 之上做平台，Smolmachines 自己试图成为更底层的 VM runtime，位置更接近 Firecracker + Docker ergonomics。
  • 本地优先 + 云端一致：smolvm 可以在本地 Mac / Linux 上运行，再用同一 artifact 部署到云端或自部署环境，这比纯 cloud sandbox 更适合开发者调试和离线/私有环境。
  • 弹性资源与 fork 机制：创始人声称 VM 内建 fork primitive，fork 只支付父 VM 基础成本加每个子 VM 差量，适合 agent 并行尝试、分支执行、短生命周期 workload。
  • 早期 open-source mindshare：上线时间短但已有 4.1k+ GitHub stars，说明开发者对“portable VM as container replacement”有明显兴趣。

我们的押注

  1. 赛道 beta：agent 时代的安全执行边界会从 container 回到 VM。AI agent 运行的是模型实时生成、用户没有读过的代码，威胁模型比传统 DevOps 更接近“不可信租户”。IOSG 6-24 sandbox research 的核心判断是 agent sandbox 的价值会向有状态运行时、多云中立和隔离边界迁移；Smolmachines 正好押在这条边界重画上。
  1. 公司 alpha：Smol 不只是 sandbox provider，而是在争取成为 Firecracker 之后的新开发者 VM primitive。如果 E2B / Daytona / Vercel 是上层 sandbox 产品，Smolmachines 的野心是让开发者直接把微型 VM 当作 container replacement 使用。本地可跑、单文件 artifact、云端一致部署和 fork primitive 如果成立，会让它拥有比单点 cloud sandbox 更底层的开发者心智。
  1. 结构性不对称：$35M cap 买的是一个高难度底层 infra call option。同赛道上层平台已经出现 E2B $32M funding、Daytona $24M Series A、Modal $4.65B post-money 的资金验证；Smol 当前只有 1 人团队和早期开源 traction，但如果能被 agent builders 采纳为 portable VM layer，$35M cap 的风险收益不差。$50k 额度更像 access / relationship / portfolio adoption option，而不是重仓财务配置。
  1. GTM 飞轮：开源开发者 mindshare + portfolio workloads 可帮助其穿过 trust gap。创始人自己也承认客户犹豫点是 production trust，而非 demo 速度；这类底层 infra 最难的往往是“敢不敢跑生产 workload”。IOSG 若能让少数 AI portfolio 以低风险非核心 workload 试用，既能帮助 DD，也能让小 check 产生实际网络价值。
  1. 可验证护城河：真正的壁垒不是 200ms cold start，而是 VM artifact、fork 和弹性计费是否能在真实 workload 中稳定成立。冷启动本身会被 Firecracker、gVisor、Docker 优化快速追平；Smol 的可防守性要来自更完整的 developer workflow：本地调试、可移植 artifact、差量 fork、按 active resource 计费和隔离默认值。后续 DD 应把这些当作可验证 falsifier，而不是接受 demo 表述。

风险

  • 生产信任是核心瓶颈，且需要时间和真实 workload 证明。创始人已明确承认潜在客户测试后仍不信任新 VM runtime；底层 compute infra 一旦出稳定性、安全或兼容性问题，客户迁移成本和声誉损失都很高。
  • 竞争层级复杂，既有大厂也有上层平台挤压。E2B / Daytona 抢 developer API 心智，Modal / Vercel / Cloudflare / AWS 可通过已有云平台分发 sandbox primitive；Smol 如果不能证明“更底层”带来的不可替代价值，可能被视为 feature / open-source tool 而非公司。
  • 商业化指标仍很薄。目前只有“几千 VM/day”和若干早期客户名，缺少 ARR、付费客户数、留存、gross margin、平均 VM 时长、事故率、单位经济和 customer concentration 数据；无法判断 usage-based model 是否能支撑 venture-scale revenue。
  • 团队单点风险高。YC 页面显示 1 人团队，项目又是高复杂度底层 infra，涉及 hypervisor、kernel、networking、storage、安全和云平台运维；招聘和工程执行速度将直接决定是否能从 demo 走到 production trust。
  • 投资方/轮次信息需清理。通话自动转录与 Slack thread 对投资方名称存在不一致，Robinhood / Robin Hood、Vermilion / Veridian / Vendril、Eniac 是否已投需要 cap table 或 financing docs 验证。
